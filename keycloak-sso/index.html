● Existing Keycloak owner

Start with a scoped invitation.

Sign in with your existing Keycloak administrator account. Links opens with active setup links across accessible realms: unexpired invitations waiting to start or in progress. Search the paged Realm and Organization filters to narrow the list, then choose the realm for a new link.

Check one or more organizations, or choose Realm Connection (no orgs). No configured domains are needed. Set the protocol, expiry and testing policy, then share the link with the customer's identity-provider administrator.

Your backend can do this too. Issue setup links through the REST API using an authorized Keycloak service account.

One invitation creates one connection, shared by every selected organization.

See the links home ↗

● Customer's IdP administrator · screen 1 of 4

Create the application at your provider.

Open the invitation and choose Custom OIDC or Custom SAML. The invitation determines which buttons are available.

The invitation works until it expires, is revoked or setup completes. Active work keeps the session open. After 30 minutes of inactivity by default, reopen the original invitation to start again; previous draft settings and tests are cleared. An update restart leaves the live connection unchanged.

Copy the exact Redirect URI / callback URL into a confidential OIDC application at your provider. Use Authorization Code; Keycloak exchanges the code on the server.

Save the application and keep its client ID and credential ready for the next screen.

Copy both the Assertion consumer service (ACS) URL and SP entity ID / Audience URI into a SAML application at your provider.

Both values are available before you enter the provider configuration. Keep its metadata URL ready for the next screen.

Register the exact values. The callback belongs to this connection. A realm address alone does not replace it.

● Customer's IdP administrator

Connect the customer's identity provider.

Enter the OpenID configuration URL, client ID and client secret. If the invitation uses another authentication method, supply the credential it asks for.

Automatic imports the provider endpoints when you continue. You can upload or paste its configuration document instead. Manual entry is an Advanced fallback. When editing a saved OIDC draft, its imported provider URLs stay under Advanced; mapping changes do not require re-entering them.

The client secret field remains visible when editing. The saved value stays hidden and is kept unless you choose Replace saved client secret.

Automatic needs the provider's SAML metadata URL, or an uploaded/pasted XML document.

Manual needs its entity ID, sign-on URL and public signing certificate. Request signing and HTTP Redirect/POST binding are under Advanced; requirements from imported metadata stay enforced.

Required or optional? Fields marked * are required. Most setups can leave Advanced closed.

● Customer's IdP administrator · screen 3 of 4

Identify the account. Map its details.

OIDC uses sub as the account identifier. Profile mappings copy details such as email and name; they do not replace that ID.

Choose a stable Subject NameID or identity attribute. A transient NameID needs a separate stable identity attribute. Email or username profile mappings do not replace the identifier.

Profiles supply the starting mappings and required fields. Edit permitted sources, Remove optional mappings, or choose an approved user field and Add mapping. Approve extra fields in Realm settings. The provider supplies the values; destination fields stay fixed.

Mapping rules belong to the connection; values are stored on the user in that realm. Removing a mapping does not erase saved values. Keycloak may still import standard OIDC profile claims automatically.

Save, then test. Choose Create connection to save the configuration and open the test screen. Activation happens after testing.

● Customer's IdP administrator

Confirm one stable identity.

When two tests are required, sign in twice with the same identity-provider account. Both must return the same user ID; the second asks for fresh authentication. This compares returned identities, not how the provider authenticated the person.

4. Test sign-in. Run the first test, then the second when required. A different account or missing required claim is explained on this page. Correct the settings or restart the check, then test again. Closing the sign-in window lets you retry.

Open Test details under either result to inspect the user ID and available verified OIDC claims and UserInfo, or SAML NameID and attributes, including failed claim validation. Use Copy JSON to copy the displayed response. Tokens and credentials are hidden. Preview size limits can shorten values or omit claims. Details expire after 15 minutes and stay out of activity logs and notifications.

Back preserves edits while you review earlier steps. Cancel editing restores the saved draft. Saving changes clears earlier test results. Complete the tests required by the invitation before activation.

A draft is the saved test connection. Activation makes it live; an update keeps the current connection in use until you apply the tested changes.

See the sign-in window ↗
Tests do not create users. The checks confirm a repeatable provider identity. They leave Keycloak users and linked accounts unchanged.

The two-test policy is optional for new setup links. When enabled, it cannot be bypassed.

● Customer's IdP administrator

Put the connection into service.

Choose Activate connection at the bottom of the Test sign-in screen. Required confirmation must still be fresh: it lasts 15 minutes. There is no separate activation step to navigate to.

The saved connection keeps every organization selected in the invitation. Your team can then verify an ordinary application sign-in. Optional Support and Return actions appear after successful activation, so the customer can open help or go back to your application.

Update the same connection later. Open Connections and choose Create update link on its row. Its existing organizations stay attached.

Keycloak continues to own users, sessions and access decisions.

Reusable rules and defaults

Choose the scope.
Keep the chosen realm.

Named Instance and Realm switches make the scope explicit. Instance scope requires instance administrator access; switching scope preserves the selected realm.

Instance profiles

Save shared setup rules for use across realms. A link still targets one realm and its authorized organizations.

Realm profiles

Profiles supply default mappings, required fields and source-editing rules. A shared instance profile can be reused across realms; custom fields still need to exist and be approved in each destination realm for new connections.

Instance settings

Set shared defaults once. Under After-setup links, enter an optional full HTTPS Support URL for help and Return URL for your application. Each realm inherits both values.

Realm settings

Under Approved custom fields, choose existing fields from this realm’s Keycloak User profile. Customers can add them during new connection setup, even when they are absent from profile defaults. The extension does not create user fields. Each invitation keeps its saved list; changes affect future invitations.

For new connections, missing or unapproved required profile fields prevent link creation; unavailable optional defaults are omitted. Update links retain their profile’s existing mapping rules. Optional Support and Return URLs inherit independently from instance settings and appear after successful setup; a profile can override either destination.

Brand the customer setup page.

In a profile, Setup page branding sets your brand name, logo, button color and header color. You can also replace the welcome heading and message. Each invitation keeps the branding it was issued with.

Use an instance profile across realms, or a realm profile for a separate brand. Your identity provider controls its own sign-in page.

For your backend

Create the invitation.
Let your customer finish setup.

Your backend issues a setup link. The customer administrator opens it, supplies their identity provider settings, tests sign-in and activates the connection.

  1. Prepare a Keycloak access token

    Use a Keycloak administrator or service-account token authorized for the target realm and organizations. On Keycloak 26.8.2, attach the built-in kc-admin-api client scope to your backend client, as a default or requested optional scope. Its mapper supplies the required Admin API audience.

    Token example and required permissions ↓

  2. Create a link for one organization

    Replace the example host, access token and organization ID. customer-portal is the realm’s name in the URL. The UUID in organizationIds is the organization’s native ID, not its name or alias.

    curl --request POST \
  'https://sso.northstar.example/admin/realms/customer-portal/idp-setup-links' \
  --header 'Authorization: Bearer YOUR_ACCESS_TOKEN' \
  --header 'Content-Type: application/json' \
  --data '{"organizationIds":["34d59e94-2a6c-42f3-b969-006c54613d1f"]}'

    That is the complete minimal request. It uses the realm’s default profile, then the instance default, or standard rules if neither is set. Standard rules offer OIDC and SAML and a seven-day invitation. Find your IDs below.

  3. Send the returned URL to the customer administrator

    A successful request returns 201 Created. This response excerpt shows the fields your backend needs:

    {
  "id": "6a7eb764-3696-46f0-ac87-e7779e398522",
  "status": "ACTIVE",
  "setupUrl": "https://sso.northstar.example/realms/customer-portal/idp-setup#ticket=EXAMPLE_ONE_TIME_TICKET"
}

    Share setupUrl privately. It is a bearer credential: whoever has the URL can use the invitation. It is returned only at creation; revoke and replace a lost link. Keep the invitation id to track or revoke it. ACTIVE means the customer has not started yet.

Choose protocols, expiry and tests — or share one connection

Use the same POST endpoint and headers. This fuller example selects a saved profile and requests one OIDC connection shared by two organizations, with a one-day invitation and two successful sign-ins required before activation:

{
  "purpose": "CREATE",
  "organizationIds": [
    "34d59e94-2a6c-42f3-b969-006c54613d1f",
    "f1493eb3-3fa3-4350-953d-d1807c053f99"
  ],
  "allowedProviderTypes": ["oidc"],
  "expirationSeconds": 86400,
  "requireTwoSuccessfulTests": true,
  "profileId": "YOUR_PROFILE_ID",
  "profileRevision": 1
}

Replace the profile ID and revision with an enabled profile’s id and latest revision, or omit both to use the default selection. Use 1–50 unique organization IDs and permission for every selected organization. organizationId also accepts a single ID; send one organization field, never both. No organization domain is required.

Optional invitation settings
FieldWhat to send
allowedProviderTypesAn array: ["oidc"] for OpenID Connect, ["saml"] for SAML, or ["oidc", "saml"] for both. Omit it, or send an empty array, to use the profile’s protocols. Values are lowercase.
expirationSecondsAn integer from 1 to the effective profile’s maximum. Omit for its default. Standard rules default to 604800 (7 days), with a maximum of 2592000 (30 days).
requireTwoSuccessfulTeststrue requires two fresh sign-ins with the same stable account ID. Omitted or false preserves the profile’s requirement; it cannot disable required tests. Standard rules default to false.
profileIdThe id of an enabled realm or shared instance profile. Omit to use the default selection described above. A shared profile supplies rules; the request still targets one realm and its authorized organizations.
profileRevisionA positive integer, only with profileId. Omit to select that profile’s latest revision. If supplied, it must be the latest revision and the profile must be enabled.

Request options must fit the effective profile’s rules: OIDC must be allowed and the lifetime must be within its maximum. A profile requirement for two tests cannot be disabled.

Invite a customer to update an existing connection

POST to the same endpoint with an update purpose. This issues a new invitation to update the connection. It does not edit an earlier setup link or change the live connection immediately.

curl --request POST \
  'https://sso.northstar.example/admin/realms/customer-portal/idp-setup-links' \
  --header 'Authorization: Bearer YOUR_ACCESS_TOKEN' \
  --header 'Content-Type: application/json' \
  --data '{
    "purpose": "ROTATE_CREDENTIALS",
    "targetIdentityProviderId": "9b387fc5-e6cc-43c9-87dd-57f30945ebd7"
  }'

targetIdentityProviderId is the connection’s immutable native id from GET …/connections. It is different from an invitation ID, an organization ID and the connection’s alias. Omit both organization fields: the update inherits every existing organization association. Omit allowedProviderTypes; the connection fixes the protocol.

Exact purpose values
ValueWhat the recipient can do
CREATEConfigure a new connection. This is the default when purpose is omitted, null or blank. Do not send a target connection ID.
ROTATE_CREDENTIALSReplace the target’s OIDC client secret or SAML verification certificates. A successful sign-in test is required; the effective profile may require two.
MAINTAINMake only the changes allowed by a saved profile’s maintenance capabilities. The effective saved profile must permit at least one capability and require two successful tests.

For broader maintenance, replace the request body with the following, using an enabled profile configured for the changes you want to delegate:

{
  "purpose": "MAINTAIN",
  "targetIdentityProviderId": "9b387fc5-e6cc-43c9-87dd-57f30945ebd7",
  "profileId": "YOUR_MAINTENANCE_PROFILE_ID"
}

A realm or instance default can supply the saved maintenance profile instead. Set its rules in Profiles: passing requireTwoSuccessfulTests: true in the invitation request does not replace the profile’s two-test requirement.

Maintenance capability codes for profile authors

These belong to a profile’s policy.maintenanceCapabilities array, not the invitation request. Every nonempty capability set requires policy.requireTwoSuccessfulTests: true.

CREDENTIAL_ROTATION
Change credentials.
ENDPOINTS
Change protocol endpoint URLs.
DISPLAY_NAME
Change the connection’s display label.
PROFILE_MAPPINGS
Change profile field mappings within the profile’s rules.
CERTIFICATE_ADD
Add SAML verification certificates.
CERTIFICATE_REPLACE
Replace SAML verification certificates.
CERTIFICATE_RETIRE
Retire SAML verification certificates.

Updates require authority over every organization using the connection. They also require native manage-identity-providers authority unless the connection allows delegated updates (kc.setup.delegated-updates=true, set on connections created through setup links). Update invitations cannot skip testing.

Find IDs, list invitations and revoke a link

Use your administrator bearer token for these GET requests. Every path below starts at your Keycloak host and uses the realm name customer-portal.

GET /admin/realms/customer-portal/idp-setup-links/organizations?search=northstar&first=0&max=50
GET /admin/realms/customer-portal/idp-setup-links/connections?organizationId=YOUR_ORGANIZATION_ID&first=0&max=50
GET /admin/realms/customer-portal/idp-setup-links/profiles?organizationId=YOUR_ORGANIZATION_ID&first=0&max=50
Organizations
A JSON array. Use each organization’s id in organizationIds. Search matches its name, alias or ID.
Connections
An object with items, total, first and max. Use an item’s id as targetIdentityProviderId. updateAllowed reports update eligibility for the caller.
Profiles
A JSON array of enabled profiles. Use id as profileId and, if pinning it, revision as profileRevision.

Only authorized results are returned. first is a zero-based offset; max is the page size. Use max=50 for all three requests and advance first to 50, then 100, and so on. For array responses, continue until an empty array. For paged objects, stop when first + items.length >= total. Organizations, connections and invitations cap max at 200; profiles accept 1–100.

To track invitations or revoke one, use:

GET /admin/realms/customer-portal/idp-setup-links?activeOnly=true&first=0&max=50
DELETE /admin/realms/customer-portal/idp-setup-links/YOUR_INVITATION_ID

The list has the same paged-object shape as connections. activeOnly=true includes unexpired invitations that are not started, being configured or being tested. It excludes completed, revoked and expired invitations. status=ACTIVE means only Not started. A successful DELETE returns 204 No Content.

To add organizations directly to a saved connection, POST {"organizationIds":["YOUR_ADDITIONAL_ORGANIZATION_ID"]} to /admin/realms/customer-portal/idp-setup-links/connections/YOUR_CONNECTION_ID/organizations. This adds native associations without removing existing ones or issuing an invitation. It requires authority for every current and added organization, plus the update authority described above.

Token setup, permissions and realm connections

For a backend service account, enable client authentication and service accounts on your Keycloak client. Assign its service account the permissions needed for this realm. Keep the standard roles client scope and its role mappers. Attach the built-in kc-admin-api client scope as a default scope, or as an optional scope and request it when obtaining the token:

curl --request POST \
  'https://sso.northstar.example/realms/customer-portal/protocol/openid-connect/token' \
  --header 'Content-Type: application/x-www-form-urlencoded' \
  --data-urlencode 'grant_type=client_credentials' \
  --data-urlencode 'client_id=YOUR_BACKEND_CLIENT_ID' \
  --data-urlencode 'client_secret=YOUR_BACKEND_CLIENT_SECRET' \
  --data-urlencode 'scope=kc-admin-api'

Take access_token from the response and use it in the API’s Authorization: Bearer … header. Keep client credentials and administrator tokens on your backend. The customer receives only the setup URL.

For the service-account example, assign the realm-management client roles manage-realm and manage-identity-providers. If Full Scope Allowed is disabled, include the needed roles in the client’s role scope mappings. A delegated organization issuer instead needs the existing manage-idp-setup-links realm role and native manage permission for every affected organization. The client scope supplies the Admin API audience; it does not grant these permissions.

For a realm connection, send {} to the creation endpoint. With no organization fields, this creates a connection outside an organization. It requires native realm and identity-provider administration, and deployment policy must allow realm-wide links (KC_IDP_SETUP_ALLOW_REALM_WIDE_LINKS). Check the caller’s current access with:

GET /admin/realms/customer-portal/idp-setup-links/access

realmWideAllowed must be true for that request. Omitting organization IDs never bypasses permission checks.

401
Check token validity and the native kc-admin-api scope and Admin API audience.
403
Check issuer permissions, every affected organization, update authority and realm-wide policy.
409 + unsafe_first_broker_login_flow
For CREATE, the realm owner must fix the default first broker login flow so it does not automatically link existing accounts.
Optional: approve custom profile fields by API

Realm owners can approve existing Keycloak User Profile fields for new connections. Read availableMappingFields and approvedMappingFields, then save the approved names:

GET /admin/realms/customer-portal/idp-setup-links/profiles/settings

PUT /admin/realms/customer-portal/idp-setup-links/profiles/settings/mapping-fields
Authorization: Bearer YOUR_ACCESS_TOKEN
Content-Type: application/json

{"approvedMappingFields":["employeeId","department"]}

Approve up to 32 existing custom fields; an empty list clears approval. This does not create fields or change profile defaults. A missing or unapproved required profile field blocks CREATE with required_mapping_unavailable. Instance settings have no field catalogue. Update invitations keep their profile’s mapping rules.

For the full API reference, open the SSO Setup Links owner panel → User guide → API. Find the owner panel URL.

Installation footprint

One provider JAR.
Your existing Keycloak.

Both interfaces ship with the extension. No separate frontend service, plugin database or runtime Node installation is required.

Tested baseline Keycloak 26.8.2

  1. 01

    Add the extension to your server image.

    Place the JAR in Keycloak's providers/ directory, then run bin/kc.sh build before starting the optimized server.

  2. 02

    Use your existing deployment configuration.

    Keep the host's supported database and connection settings. Configure the plugin's shared rate-limit key and deployment policy alongside your public hostname, proxy and TLS settings.

  3. 03

    Open the owner panel.

    Use your existing Keycloak administrator login. The plugin has a separate panel; it is not a menu inside the native Admin Console.

Open the built-in user guide

In your installation, open SSO Setup Links and choose User guide. It includes setup instructions and the full API reference. Sign in with your existing Keycloak administrator account.

Built-in guide URL pattern · replace the example hostname with yourshttps://sso.northstar.example/realms/master/idp-setup/admin?guide=1#start

The JAR adds its own metadata tables through Keycloak's existing database connection. Owner-managed setup profiles and permitted branding live in the panel; infrastructure secrets and server settings remain deployment configuration.

Normal organization sign-in can require Keycloak email verification; configure native realm SMTP when needed. Setup tests do not create users or send verification emails.

Keep tracing disabled on this baseline because of the host's OpenTelemetry advisory. Qualify a patched host before enabling it.
