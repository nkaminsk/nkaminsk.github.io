● Existing Keycloak owner

Start with a scoped invitation.

Sign in with your existing Keycloak administrator account. Links opens with active setup links across accessible realms: unexpired invitations waiting to start or in progress. Search the paged Realm and Organization filters to narrow the list, then choose the realm for a new link.

Check one or more organizations, or choose Realm Connection (no orgs). No configured domains are needed. Set the protocol, expiry and testing policy, then share the link with the customer's identity-provider administrator.

Your backend can do this too. Issue setup links through the REST API using an authorized Keycloak service account.

One invitation creates one connection, shared by every selected organization.

● Customer's IdP administrator

Connect the customer's identity provider.

Open the invitation and register an application with the customer's OpenID Connect provider. Enter its discovery or endpoint details and client credentials.

Register the exact callback shown by the wizard. Then choose the stable identity and map the profile fields your application needs.

See the mapping defaults ↗

Open the invitation and import the customer's SAML metadata, or enter its entity ID, sign-on URL and signing certificate.

Choose a stable NameID or released identity attribute. Once the draft is saved, register its exact ACS URL or import the generated service-provider metadata.

See the SAML registration screen ↗
Mappings start with useful defaults. Profiles prefill source claim or attribute names; the provider supplies their values. Recipients can edit permitted sources and omit optional mappings. Required and locked rules stay enforced. The stable account ID is separate; native OIDC profile imports still apply.

The wizard saves a hidden draft before testing.

● Customer's IdP administrator

Confirm one stable identity.

Sign in twice with the same identity-provider account. Both tests must return the same stable account ID; the second test asks for fresh authentication.

A different account or changing ID fails the comparison. The same test pair checks the connection when several organizations share it.

See a different-account rejection ↗
Tests do not create users. The checks confirm a repeatable provider identity. They leave Keycloak users and linked accounts unchanged.

The two-test policy is optional for new setup links. When enabled, it cannot be bypassed.

● Customer's IdP administrator

Put the connection into service.

Review the configuration and activate while the required test results are current. The draft becomes a native Keycloak identity provider.

The saved connection keeps every organization selected in the invitation. Your team can then verify an ordinary application sign-in. Optional Support and Return actions appear after successful activation, so the customer can open help or go back to your application.

Update the same connection later. Open Connections and choose Create update link on its row. Its existing organizations stay attached.

Keycloak continues to own users, sessions and access decisions.

01 / SCOPE

Choose who shares the connection.

Search organizations by name or alias in pages of 20; selections stay visible across pages. Select up to 50 organizations per plugin request, or use a realm connection. This does not limit the organizations in Keycloak.

02 / PROFILES

Reuse the rules you need.

Profiles save protocols, mappings, lifetime, tests, allowed updates and branding. Optional Support and Return URLs can inherit your settings or use profile-specific values. Each new invitation copies its rules; profile edits affect future invitations.

03 / UPDATES

Keep an existing connection current.

Issue a link for credential replacement or changes allowed by a profile. The customer updates that connection; its organization associations stay in place.

Instance settings supplies shared defaults. Realm settings chooses defaults for one realm, including its Default profile and optional backend notification. The separate Deployment information dropdown shows read-only server configuration.

Realms inherit each value unless they override it; an explicit profile URL takes precedence. New invitations save the resolved URLs, so later settings edits affect future links. An existing invitation’s button may disappear if you remove its website from your settings.

Reusable rules and defaults

Keep the chosen realm.

Named Instance and Realm switches make the scope explicit. Instance scope requires instance administrator access; switching scope preserves the selected realm.

Instance profiles

Save shared setup rules for use across realms. A link still targets one realm and its authorized organizations.

Realm profiles

Manage setup rules for the chosen realm. Switch back from Instance profiles with the same realm ready to use.

Instance settings

Set shared defaults once. Under After-setup links, enter an optional full HTTPS Support URL for help and Return URL for your application. Each realm inherits both values.

Realm settings

Leave a URL blank to inherit its instance value, or override either field for this realm. An explicit profile URL wins. Both optional actions appear after successful setup or update and open only when clicked.

For your backend

The same scoped invitation.
A small API request.

The realm’s name goes in the URL; native organization IDs go in the JSON body. Use a Keycloak bearer token with permission for every affected organization.

POST https://YOUR-KEYCLOAK/admin/realms/partner-demo/idp-setup-links
Authorization: Bearer <access-token>
Content-Type: application/json

Create one connection for two organizations

{
  "organizationIds": ["<org-id-a>", "<org-id-b>"]
}

For one organization, use {"organizationId":"<org-id>"}. Send one organization field, never both.

Create a credential-update link

{
  "purpose": "ROTATE_CREDENTIALS",
  "targetIdentityProviderId": "<immutable-connection-id>"
}

Use the connection’s immutable ID, not its name. Omit organization fields: the server derives and checks all its existing associations.

Accepted values

purpose
  • CREATE (default) — create a new connection.
  • ROTATE_CREDENTIALS Replace credentials only.
  • MAINTAIN Make changes permitted by a profile.
allowedProviderTypes

An array containing either or both of these exact lowercase values:

  • "oidc" OpenID Connect.
  • "saml" SAML.
Optional fields and a full example ↓

The response contains a setup URL. Send it privately to the customer administrator. The API issues the invitation; the customer supplies settings and completes the wizard.

Optional fields and a full example 
{
  "purpose": "CREATE",
  "organizationId": "<org-id>",
  "allowedProviderTypes": ["oidc"],
  "expirationSeconds": 86400,
  "requireTwoSuccessfulTests": true,
  "profileId": "<profile-id>",
  "profileRevision": 1
}
expirationSeconds
Integer lifetime in seconds, within the profile’s limit. Omit for the configured default.
requireTwoSuccessfulTests
Boolean. true requires two matching sign-ins; it cannot weaken a profile’s requirement.
profileId / profileRevision
Select an enabled profile and optionally its latest enabled revision. Omit both for the configured default or standard rules.

For a shared connection, replace organizationId with organizationIds. No organization domain is required.

Optional settings can narrow the profile’s rules, never weaken them.

Find IDs and other actions

GET /?activeOnly=true&first=0&max=50 under the API base above lists unexpired invitations waiting to start or in progress. Completed, revoked and expired invitations are excluded. The exact status=ACTIVE filter means Not started only.

Under the API base above, GET /organizations?search=acme&first=0&max=20 searches organization names and aliases and returns their IDs. Follow pagination for later results. GET /connections?organizationId=<org-id> returns connection IDs in items. Discovery respects the caller’s permissions.

For broader connection changes, use purpose: "MAINTAIN" with a saved profile that permits the changes and requires two tests.

To add organizations directly, send {"organizationIds":["<additional-org-id>"]} to POST /connections/<immutable-connection-id>/organizations. This adds native associations without removing existing ones or issuing an invitation.

Installation footprint

One provider JAR.
Your existing Keycloak.

Both interfaces ship with the extension. No separate frontend service, plugin database or runtime Node installation is required.

Qualified baseline Keycloak 26.8.1

  1. 01

    Add the extension to your server image.

    Place the JAR in Keycloak's providers/ directory, then run bin/kc.sh build before starting the optimized server.

  2. 02

    Use your existing deployment configuration.

    Keep the host's supported database and connection settings. Configure the plugin's shared rate-limit key and deployment policy alongside your public hostname, proxy and TLS settings.

  3. 03

    Open the owner panel.

    Use your existing Keycloak administrator login. The plugin has a separate panel; it is not a menu inside the native Admin Console.

Owner panel URL patternhttps://YOUR-KEYCLOAK/realms/master/idp-setup/admin

The JAR adds its own metadata tables through Keycloak's existing database connection. Owner-managed setup profiles and permitted branding live in the panel; infrastructure secrets and server settings remain deployment configuration.
